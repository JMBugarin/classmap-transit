# Operations

Single-host deployment: one Linux VM running `compose.yaml` (PostgreSQL 17.12 plus the API image). Nothing here has run in the cloud yet. Local drill results are in `docs/evidence/operations/`.

## Images

Build one immutable image per commit and tag it with the short SHA:

```
docker build -t classmap-transit:$(git rev-parse --short HEAD) .
```

`compose.yaml` runs `classmap-transit:${TAG}`, so a deploy is always a tag switch, never a rebuild on the host.

## Deploy and rollback

```
ops/deploy.sh <tag>     # starts the tag, waits up to 60 s for /readyz, records it in .deploy/current
ops/rollback.sh         # redeploys the tag in .deploy/previous
```

If readiness fails, `deploy.sh` puts the previous tag back and exits non-zero. The schema is additive (`CREATE ... IF NOT EXISTS`, `schema_versions`), so an older image runs against a newer database as long as no migration drops or renames anything. A destructive migration needs a backup first and a manual plan; rollback alone won't cover it.

## Configuration

Set these in a `.env` next to `compose.yaml` (gitignored): `POSTGRES_PASSWORD`, `ADMIN_TOKEN`, `ALLOWED_ORIGIN`, `POLL_URL`, `SCHEDULE_VERSION`. The poller refuses intervals under 30 s. The API listens only on `127.0.0.1:${API_PORT:-8080}`. Put a TLS reverse proxy in front of it before exposing it.

## Retention

```
docker compose run --rm -e RETAIN=168h api prune
```

This deletes captures, plus their fetches, jobs, outcomes and observations, when nothing has fetched them within `RETAIN` (default 7 days, minimum 1 h). It keeps every published generation (`feed_state`) and every capture whose job is pending or running. It works in batches of 1,000 rows per transaction, so it doesn't hold long locks. Run it daily from cron.

Sizing: one METRO TripUpdates snapshot was 61 KB (`fixtures/metro-trips.pb`). At one poll per 30 s that is at most 2,880 captures and about 176 MB of raw protobuf per day, before deduplication by hash. Seven days of retention is about 1.2 GB of raw captures plus observations, which fits comfortably on a 20 GB volume.

## Backup and restore

```
ops/backup.sh                          # pg_dump -Fc inside the db container, writes backups/<db>-<utc>.dump and .sha256
ops/restore.sh <dump> transit_restore  # verifies the checksum, restores into a new database in one transaction
ops/reconcile.sh <db>                  # row counts and content digests per table
```

To replace a broken live database: stop the API (`docker compose stop api`), restore into a new database, compare `reconcile.sh` against the last good report, rename databases (`ALTER DATABASE transit RENAME TO transit_broken; ALTER DATABASE transit_restore RENAME TO transit`), then start the API and confirm `/readyz` and `/v1/feed-status`.

Data loss window: with a daily backup, up to 24 h of realtime captures can be lost. Schedules can be re-imported from the published GTFS zip, and live predictions are regenerated by the next poll after restart. So a restore loses history, not current service. Copy dumps off the host (EBS snapshot or object storage). A backup on the same disk doesn't protect against losing the volume.

## Local drill

```
docker build -t classmap-transit:<old> <old checkout>
docker build -t classmap-transit:<new> .
ops/drill.sh <old> <new>
```

The scripts use `docker compose` and fall back to a standalone `docker-compose`.

This runs in a separate compose project (`transit-drill`, API on port 18181). It deploys the old tag, imports the real METRO schedule fixture, ingests the recorded capture, deploys the new tag, rolls back, takes a backup, restores it into `transit_restore`, checks that the reconcile reports are identical, and serves the restored database from the new image.

Drill on 2026-11-15, images `10e37d2` (old) and `837e1b6` (new), Docker on a Colima VM on one laptop (`docs/evidence/operations/drill.txt`):

| Step | Result |
|---|---|
| Deploy old, import METRO schedule, ingest capture | generation 1 published, 235,038 stop_times |
| Deploy new tag (container recreate to `/readyz`) | 338 ms |
| Roll back to old tag | 587 ms, same generation served |
| Backup (`pg_dump -Fc`) | 885 ms, 6.5 MB |
| Restore into `transit_restore` | 1,131 ms, checksum OK |
| Reconcile source vs restored | identical on all 9 tables |
| New image on the restored database | serves generation 1 |

`837e1b6` is the pre-rebase commit of the deploy scripts. After rebasing onto the benchmark merge it is `27a10c9`, which only adds the `bench-seed` subcommand from main. These are local timings on a tiny dataset. They aren't cloud recovery times and don't include provisioning, DNS or copying the dump between hosts. The `prune` command was also run against the drill database (`prune-cli.txt`).

## Cost estimate (before any spend)

Prices checked November 14, 2026, US West (Oregon), on-demand Linux. The EC2 rates come from AWS's published price map dated 2026-11-14. The public IPv4 rate is from the VPC pricing page. The gp3 and snapshot rates are the example rates on the EBS pricing page and must be confirmed in the AWS Pricing Calculator before D02.

| Item | Rate | 30 days (720 h) |
|---|---|---|
| t4g.small (2 vCPU, 2 GiB) | $0.0168/h | $12.10 |
| Public IPv4 address | $0.005/h | $3.60 |
| gp3 root volume, 20 GB | $0.08/GB-month | $1.60 |
| EBS snapshots, ~10 GB changed data | $0.05/GB-month | $0.50 |
| Data transfer out | under 1 GB/month expected | $0 if within the free 100 GB/month |
| **Total** | | **≈ $17.80/month** |

A t4g.micro (1 GiB, $0.0084/h) brings this to about $11.75/month, but 1 GiB is tight for PostgreSQL plus the API. Recommended budget: a $25/month AWS Budgets alert at 50%, 80% and 100%, with no reserved capacity and no free-tier assumption. Nothing is provisioned until that budget and credentials exist.
