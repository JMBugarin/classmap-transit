# Operations

Single-host deployment: one Linux VM running `compose.yaml` (PostgreSQL 17.12 plus the API image). It runs on one EC2 t4g.small in us-west-2 since 2026-11-17 (see Cloud deployment below). Local drill results are in `docs/evidence/operations/`, cloud results in `docs/evidence/cloud/`.

## Images

Build one immutable image per commit and tag it with the short SHA:

```
docker build -t classmap-transit:$(git rev-parse --short HEAD) .
```

`compose.yaml` runs `classmap-transit:${TAG}`, so a deploy is always a tag switch, never a rebuild on the host.

## Deploy and rollback

```
ops/deploy.sh <tag>     # starts the tag, waits up to 60 s for /readyz, records it in .deploy/current
ops/rollback.sh         # redeploys the tag in .deploy/previous
```

If readiness fails, `deploy.sh` puts the previous tag back and exits non-zero. The schema is additive (`CREATE ... IF NOT EXISTS`, `schema_versions`), so an older image runs against a newer database as long as no migration drops or renames anything. A destructive migration needs a backup first and a manual plan; rollback alone won't cover it.

## Configuration

Set these in a `.env` next to `compose.yaml` (gitignored): `POSTGRES_PASSWORD`, `ADMIN_TOKEN`, `ALLOWED_ORIGIN`, `POLL_URL`, `SCHEDULE_VERSION`. The poller refuses intervals under 30 s. The API listens only on `127.0.0.1:${API_PORT:-8080}`. Put a TLS reverse proxy in front of it before exposing it.

## Retention

```
docker compose run --rm -e RETAIN=168h api prune
```

This deletes captures, plus their fetches, jobs, outcomes and observations, when nothing has fetched them within `RETAIN` (default 7 days, minimum 1 h). It keeps every published generation (`feed_state`) and every capture whose job is pending or running. It works in batches of 1,000 rows per transaction, so it doesn't hold long locks. On the host, `ops/maintain.sh` runs daily from `ops/systemd/transit-maintain.timer` (11:00 UTC): backup, prune with `RETAIN=168h`, and delete dumps older than 7 days.

Sizing: one METRO TripUpdates snapshot was 61 KB (`fixtures/metro-trips.pb`). At one poll per 30 s that is at most 2,880 captures and about 176 MB of raw protobuf per day, before deduplication by hash. Seven days of retention is about 1.2 GB of raw captures plus observations, which fits comfortably on a 20 GB volume.

## Backup and restore

```
ops/backup.sh                          # pg_dump -Fc inside the db container, writes backups/<db>-<utc>.dump and .sha256
ops/restore.sh <dump> transit_restore  # verifies the checksum (relative to the dump's directory), restores into a new database in one transaction
ops/reconcile.sh <db>                  # row counts and content digests per table
```

To replace a broken live database: stop the API (`docker compose stop api`), restore into a new database, compare `reconcile.sh` against the last good report, rename databases (`ALTER DATABASE transit RENAME TO transit_broken; ALTER DATABASE transit_restore RENAME TO transit`), then start the API and confirm `/readyz` and `/v1/feed-status`.

Data loss window: with a daily backup, up to 24 h of realtime captures can be lost. Schedules can be re-imported from the published GTFS zip, and live predictions are regenerated by the next poll after restart. So a restore loses history, not current service. Copy dumps off the host (EBS snapshot or object storage). A backup on the same disk doesn't protect against losing the volume.

## Local drill

```
docker build -t classmap-transit:<old> <old checkout>
docker build -t classmap-transit:<new> .
ops/drill.sh <old> <new>
```

The scripts use `docker compose` and fall back to a standalone `docker-compose`.

This runs in a separate compose project (`transit-drill`, API on port 18181). It deploys the old tag, imports the real METRO schedule fixture, ingests the recorded capture, deploys the new tag, rolls back, takes a backup, restores it into `transit_restore`, checks that the reconcile reports are identical, and serves the restored database from the new image.

Drill on 2026-11-15, images `10e37d2` (old) and `837e1b6` (new), Docker on a Colima VM on one laptop (`docs/evidence/operations/drill.txt`):

| Step | Result |
|---|---|
| Deploy old, import METRO schedule, ingest capture | generation 1 published, 235,038 stop_times |
| Deploy new tag (container recreate to `/readyz`) | 338 ms |
| Roll back to old tag | 587 ms, same generation served |
| Backup (`pg_dump -Fc`) | 885 ms, 6.5 MB |
| Restore into `transit_restore` | 1,131 ms, checksum OK |
| Reconcile source vs restored | identical on all 9 tables |
| New image on the restored database | serves generation 1 |

`837e1b6` is the pre-rebase commit of the deploy scripts. After rebasing onto the benchmark merge it is `27a10c9`, which only adds the `bench-seed` subcommand from main. These are local timings on a tiny dataset. They aren't cloud recovery times and don't include provisioning, DNS or copying the dump between hosts. The `prune` command was also run against the drill database (`prune-cli.txt`).

## Cloud deployment (D02)

One t4g.small (2 vCPU Graviton, 2 GiB, standard CPU credits) in us-west-2 running Amazon Linux 2023, Docker and this `compose.yaml` from `/opt/classmap-transit`. Root volume 20 GB gp3, encrypted. The security group allows only SSH from the operator's address. The API stays on `127.0.0.1:8080`, so reach it through `ssh -L 8080:127.0.0.1:8080`. There is no public endpoint or TLS yet. The poller fetches the live METRO TripUpdates feed every 60 s (`POLL_INTERVAL=60s`). Secrets live only in the host's `.env` (mode 600).

Images are built arm64 on the operator machine and shipped with `docker save classmap-transit:<tag> | gzip | ssh <host> docker load`, then `ops/deploy.sh <tag>` on the host. There's no registry.

The first cloud schedule import failed. The default 5 s `statement_timeout` cancelled the 235,038-row `stop_times` COPY on this instance, though the same import finishes in about 2.5 s on the laptop. The import transaction now sets `statement_timeout = 0` locally, and the import takes 8.9 s on the host.

### Recovery drill

`ops/cloud-drill.sh <user@host> <old> <new>` runs from the operator machine. It deploys, rolls back, takes a backup and copies it off the host. After `LOSS_WAIT` seconds of live polling it destroys the database volume with `docker compose down -v`, copies the dump back, restores it, reconciles it against the backup-time report, redeploys, and waits for a new generation. Run on 2026-11-17 with `10e37d2` as old and `dffd820` as new, `LOSS_WAIT=300` (`docs/evidence/cloud/drill.txt`):

| Step | Result |
|---|---|
| Deploy `dffd820` (already current, readiness only) | 1,818 ms |
| Deploy `10e37d2` | 2,541 ms |
| Roll back to `dffd820` | 3,160 ms, generation unchanged |
| Backup (`pg_dump -Fc`) | 2,351 ms, 6.49 MB |
| Copy dump to the operator machine | 2,753 ms, checksum OK |
| Live polling after backup | 305 s, generations 6 → 12 |
| **Failure**: database volume destroyed | 10:07:51Z |
| Copy dump back to the host | 2,613 ms |
| Start an empty database | 4,218 ms |
| Restore | 3,226 ms |
| Reconcile restored vs backup-time report | identical on all 9 tables |
| Failure → `/readyz` on `dffd820` | **18.0 s** |
| Failure → first new published generation | **19.6 s**, fresh |

Every step is timed with the host clock but includes one or two SSH connections from the laptop (553–798 ms each). The step times are upper bounds.

Data loss: the 5 captures and 5 fetches made between the backup and the failure were lost, which is 305 s of realtime history. Current service was not lost, because the poller published fresh data within 1.6 s of readiness. The data-loss window equals the time since the last backup that left the host. The daily timer writes dumps on the same volume, so after a volume loss the real window is the time since the last manual off-host copy (`scp`) or EBS snapshot. The deploy user has no S3 or Data Lifecycle Manager permissions, so off-host copies aren't automated yet.

Generation ids are capture ids. After the restore the sequence continued from the backup, so ids 7–12 were reissued for different captures (the restored service published generation 8). A client that cached a generation id from before the failure can see the same id for different data.

Fixed in schema version 2. New capture ids come from `next_capture_id()`, which takes the larger of the next sequence value and the database clock in microseconds since the Unix epoch, then moves the sequence to it. A restore can rewind the sequence but not the clock, so every id issued after a restore is larger than any id issued before the failure. This holds as long as the database host's clock doesn't step back past the time of the lost captures. Ids are about 1.8 × 10¹⁵, inside the 2⁵³ range that JSON clients read exactly. Existing ids keep their values, and the first new id after the upgrade jumps to the clock value. `TestGenerationIDsSurviveRestore` rewinds the sequence and deletes a published capture, the way restoring an older dump does, and checks that the next generation is larger than the lost one.

An EBS snapshot of the root volume (`snap-0276bf58ff4ba696c`, 3.43 GB) took 3 min 24 s. It is crash-consistent, not a database backup, and the dumps stay the primary restore path.

## Opt-in weekly activity (O02)

The Classmap app can send one ping per install per week when the student has turned on usage counting in Settings. The rules are in the collection protocol: count a participant at most once per Monday–Sunday America/Los_Angeles week, use random ids rather than IP addresses, and send no schedules, queries, locations or names.

- `POST /v1/activity` with `{"install": "<uuid v4>", "week": "YYYY-MM-DD"}`. `week` is the Monday that starts the Pacific week, either the current one or up to 5 weeks back so pings queued offline still count. A repeat for the same week is ignored. The table holds only `install` and `week`.
- `DELETE /v1/activity?install=<uuid>` is withdrawal. Turning counting off in the app calls it, and every week for that install is deleted.
- `transit activity-exclude <uuid>...` marks developer and test installs, which are then left out of every report.
- `transit activity-report [cohort.txt]` prints the finished weeks only (the current week is left out). For each week it gives `active_installs`, the opted-in installs that aren't excluded. With a cohort file it also gives `cohort_participants`. The cohort file is the private consent record: one participant code per line (the first 8 hex digits of the install id, which the app shows under the toggle), with `#` comments. Keep it off the host and out of git.

Limits: the endpoint has no authentication, so anyone could post made-up ids. `active_installs` is therefore an upper bound on installs, not a count of students. Only `cohort_participants` counts consented students. Reinstalling the app or turning counting off and on creates a new id. Students who never opt in are invisible. Publish weekly totals only.

### Public ingress

The API stays on 127.0.0.1. Phones reach the activity endpoint through the `public` compose profile: Caddy on 80/443 with automatic Let's Encrypt TLS for `PUBLIC_HOST`. It forwards only `POST`/`DELETE /v1/activity` (body up to 1 KB) and returns 404 for everything else, so ops, admin and observations stay private. Caddy writes no access log, and the client address headers are dropped before the API. Turn it on only when a TestFlight build that uses it is going out:

1. Allocate an Elastic IP and associate it with the instance, so the hostname survives stop/start. While associated it costs the same as the public IPv4 address billed now. Update SSH targets to the new address.
2. Open tcp/80 and tcp/443 from 0.0.0.0/0 in `sg-09c5a7adc88d61166`. Port 80 is only for the ACME challenge and redirect.
3. On the host, set `PUBLIC_HOST=<ip-with-dashes>.sslip.io` in `.env`, then run `docker compose --profile public up -d ingress`.
4. Build the app with `--dart-define=ACTIVITY_URL=https://<host>/v1/activity`.

To close it: `docker compose --profile public stop ingress`, then revoke the 80/443 rules.
